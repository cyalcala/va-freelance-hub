## 4. Evidence and maturity

Every material claim needs a source, evidence timestamp and window, software and
policy revision, method, coverage and limitation. Use separate labels:

- VERIFIED_CODE: the actual implementation was read.
- VERIFIED_LOCAL: a named check ran against a named revision/environment.
- VERIFIED_DEPLOYMENT: exact-version release evidence was inspected.
- OBSERVED_RUNTIME: a dated real invocation produced recorded effects.
- ACCEPTED_OUTCOME: the applicable acceptance predicate and observation window
  passed with sufficient coverage.
- INFERRED, HISTORICAL or UNKNOWN where those are the truthful alternatives.

These labels do not replace the accepted lifecycle vocabulary. Keep maturity
separate from operational state and source authority. Do not infer deployment
from local tests, source health from deploy success, or sustained supply from
one successful tick.

Preserve initial failures, negative evidence, skips, no-ops, timeouts and reruns.
A zero-dispatch tick is not an observation of a source. A report-generation date
is not its measurement window. A confidence score is not permission or ground
truth. Missing access stays UNKNOWN rather than borrowing yesterday's numbers.

For an enforcement claim trace every relevant entrypoint through call sites,
actual writes, constraints, ledger receipts, visibility and rollback. An
ENFORCED label, function name, comment or passing test for one path cannot
certify all paths. Missing enforcement is a finding, not implicit authorization
to bypass the requirement.

## 9. Truthful supply and quality measurement

Define every metric before optimizing it: name/version, semantic definition,
unit, numerator, denominator, cohort, timezone, window, source/query, ground-truth
method, missing/late data behavior, bias, minimum evidence and uncertainty.

Count canonical opportunities, not repeated sightings or receipts. Keep
publication-time evidence so current deactivation or registry changes do not
rewrite historical performance. Report current public stock separately.
Keep versioned corrected/adjudicated reports when later independent evidence
changes qualification; immutable original receipts do not freeze an incorrect
quality judgment forever. Show original and corrected values with lineage.

For complete Asia/Manila day D, let E(D) be the recorded public-exposure events
in that day. Let P(D) contain distinct qualified, authorized canonical
opportunities whose first public exposure is evidenced in E(D). Deduplicate
receipts before constructing P(D). Classify exposure events with an explicit,
validated versioned rule into exactly one primary cohort:

```text
REACTIVATION | REPLAY_RECOVERY | BACKLOG_IMPORT
            | FRESH_DISCOVERY | OTHER_NON_FRESH
```

Keep secondary provenance when several descriptions apply; the primary cohort
must still be unique. Reactivation belongs to E(D), outside P(D). A previously
unpublished item recovered by replay can enter P(D), but remains REPLAY_RECOVERY,
not FRESH_DISCOVERY. Backlog can likewise be a first publication without being
fresh supply. Report both the event cohorts and the canonical first-publication
cohorts. Unknown/future-invalid posting dates cannot prove fresh discovery.
Preserve unknowns instead of inferring freshness from a recent harvest.

```text
FreshFlow(D) = |{j in P(D) : cohort(j) = FRESH_DISCOVERY}|
```

Use a half-open time window [day start, next day start). Do not subtract
overlapping exclusions independently, double-count cross-source jobs, or paste
SQL until identifiers, joins, history, filters and schema are verified.

For the currently specified 28-day floor, all 28 complete days must be observed
and each must meet the threshold. An average above 100 with a low day is
AVERAGE ACHIEVED, FLOOR NOT ACHIEVED. Any missing day prevents certification of
that complete floor; it is UNKNOWN, not an assumed zero or pass. This is a
reporting correction, not authority to alter production thresholds.

Report raw -> valid -> normalized -> canonical unique -> fresh -> remote/PH ->
role/safety -> source-authorized -> publication-eligible -> actually public, in
the real implementation order. Record disjoint rejection reasons, lost
publication, skipped/failed work, coverage and queue age. A stock query is not a
funnel; newest created_at is not pending-work latency.

Quality needs independent evidence and dimension-specific samples. Distinguish
published error fraction, false-positive rate, false-negative rate, precision,
recall, calibration and abstention. State which denominator applies. Unrelated
PH/remote labels must not dilute each other's rates. Adjudicate uncertain labels
and conflicts; agreement between model variants is not employer ground truth.

Report sample size, selection/strata, unresolved/censored observations, point
estimate and an appropriate interval or bound. Zero failures in a small sample
does not certify a 1% or 0.5% ceiling or zero risk. Hard safety constraints still
apply independently. Snapshot yield confidence is not source permission or an
independent classifier-quality measurement.

does not establish marginal yield or recurring observation coverage.

Budget requests, bytes, CPU, memory, SQL reads/writes, index/search amplification,
retries, model calls, storage, workflow minutes and money. Name the window and
measurement source. Quota claims and free-tier capacity require current
evidence. A storage failure is not fixed by a green unrelated watchdog.

Use existing controllers before adding clocks. Multiple schedules need shared
fencing, per-slot idempotency and aggregate origin budgets; redundant triggers
do not eliminate shared storage/account failure domains. Catch up in bounded
batches and honor Retry-After/cadence. Partial feeds cannot justify mass removal.

Measure reserve readiness with exercised capabilities, current authority and
marginal yield. Several tenants on one ATS are not independent infrastructure.
Continuity includes source replacement, model/storage outage, zero-budget mode,
credential custody, offsite backups, restoration, succession and a fresh-agent
recovery drill. Long-term institutional and community policy remains in the
source masterplan; a prompt does not create an organization or funding.

## 13. Verification, release and recovery

Inspect scripts and installed dependencies first. Use pinned runtimes where
available; disclose drift and avoid unrequested installation. Check the smallest
meaningful slice, then satisfy the applicable shared verification contract.
Broaden testing when changes or unresolved risk justify it.

For behavior changes include actual failure boundaries: missing/stale authority,
wrong identity/schema, opt-out, unknown dates, malformed/empty/partial feeds,
pagination, timeout/429, duplicate execution, cross-source false merges, denied
items, provider/model/persistence failure, cap/lease races, reactivation, partial
writes, crash/resume, rollback and public/cache withdrawal.

For documentation-only changes check paths, links, examples, instruction scope,
source traceability, mathematical consistency and contradictions. Existing test
results support only their inspected scope. Record the first failure and why a
rerun was warranted; do not rerun until green and erase the original result.

If release is in the authorized scope, follow the accepted branch/release
process, preserve coherent commits, inspect remote divergence, and verify push
receipt, exact-SHA CI/deploy and affected runtime behavior. If release is outside
scope, leave a concrete reviewable local result and state that status. A push
with database/deployment side effects is not an invisible backup step.

Preserve immutable mandates and evidence. Update operational pointers by role
rather than creating competing policy. Store reproducible non-secret aggregates,
queries, software/policy versions and durable run IDs before expiring logs are
lost. Keep raw restricted content, credentials and private records out of public
Git. Database recovery requires separately governed backup/restore evidence.

Observation plans name behavior/policy revision, start and window, actual
exercises, source/sample coverage, quality and cost bounds, evidence location,
review trigger and rollback. Separate implementation completion from acceptance
that depends on future natural events.

## 14. Closeout and handoff

Update the mathematical working register and acceptance receipt for any affected
challenge. Report baseline, current outcome, unresolved constraint and next stage;
never convert a documentation milestone into a runtime completion percentage.


Use one savepoint as the canonical mutable baton and CURRENT as short navigation.
Preserve history without stacking several apparently active NEXT instructions.
Do not overwrite unresolved incidents with a generic success summary.

Report:

```text
Unit / mode / authorized deliverable:
Start, local, remote and deployed revisions:
Changed files and behavior:
Checks actually run, first failures, reruns and runtime mismatch:
Observed effect, coverage, maturity and remaining unknowns:
Policy/parameter conflicts and unchanged acceptance boundaries:
Release and backup receipt, or explicit local-only status:
Rollback / compensation / observation still required:
One next action, prerequisite, owner/controller and due time or event:
```

For supply work add stock versus fresh flow, cohorts/windows, source/family
concentration, quality uncertainty, marginal yield/cost, candidate dispositions
and whether the floor is proved, average-only, promising, constrained or unknown.
An investigation can finish with a justified rejection without achieving the
product's long-term target.

Stop only the dependent action when authority, evidence, safety or concurrency
prevents it. Continue useful independent work and explain the exact boundary.
An interruption must leave enough evidence for another maintainer to recover
without private chat. Never fabricate a percentage, capability, approval,
deployment, observation or acceptance to make a closeout look complete.
